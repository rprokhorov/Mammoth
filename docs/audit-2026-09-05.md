## Оставшиеся находки и следующий порядок исправлений

Ниже — подтверждённые по коду проблемы; перечисленные сценарии ещё нужно закрепить регрессионными тестами.
Они не устранены тремя коммитами этого этапа.

1. **P1 — потеря черновика при смене канала во время отправки.**
   `src/components/message/MessageComposer.tsx:449`: `handleSend` после `await` без проверки текущего канала вызывает
   `setText("")` и `setAttachments([])`. `App.tsx` переиспользует экземпляр редактора без ключа канала.
   Сценарий: начать отправку в A, открыть B с сохранённым черновиком, дождаться ответа A — текст B очищается,
   эффект сохранения черновика может удалить его. Нужна изоляция состояния редактора по серверу/каналу/ветке
   и проверка принадлежности завершившейся операции.

2. **P1 — неверный сервер синхронизации черновиков.**
   `src/stores/draftsStore.ts:116`: параллельные `loadFromServer(A)` и `loadFromServer(B)` завершаются без проверки актуальности;
   поздний ответ A (даже ошибка) записывает `serverId: A`. Последующий текст канала B отправляется в A.
   Ключи локальных черновиков и таймеров также не включают сервер/аккаунт. Нужны немедленная установка контекста,
   отсечение старых ответов и миграция существующих сохранённых черновиков без потери данных.

3. **P1 — неполная история после большого перерыва может считаться прочитанной.**
   `src/components/message/MessageList.tsx:130`: загружается окно вокруг непрочитанного с `limitAfter: 60`,
   но `next_post_id` нигде не обрабатывается. Более новые записи вне окна не подгружаются, затем вызывается `view_channel`.
   Нужна догрузка вперёд либо явный переход к последним сообщениям с корректным моментом отметки прочтения.

4. **P1 — HTTP-обновление может скрыть только что пришедшее WS-сообщение.**
   `src/stores/messagesStore.ts:62`: `setChannelPosts` полностью заменяет порядок записей канала.
   Если WS добавил сообщение после формирования HTTP-ответа, старый HTTP-ответ уберёт его из видимого порядка.
   Внутри одного канала одной проверки смены поколения недостаточно. Нужна согласованная политика слияния
   с учётом времени запроса, live-событий, удалений и границ загруженного окна.

5. **P2 — открытие длинной ветки ждёт отдельный запрос реакций для каждой записи.**
   `src/components/message/ThreadPanel.tsx:74`: `await Promise.all` на N запросов задерживает показ всей ветки
   до завершения самого медленного запроса. После этого `await` отсутствует повторная проверка `cancelled`.
   Показать сообщения сразу, реакции догружать ограниченно и применять только к актуальному контексту;
   использовать уже полученные `metadata.reactions`, когда они присутствуют.

6. **P2 — старые результаты поиска заменяют новые.**
   `src/components/search/SearchBar.tsx:52`: `doSearch` не проверяет актуальность запроса.
   Медленный поиск A может перезаписать быстрый B, а ответ после закрытия вернуть результаты при следующем открытии.
   Нужен счётчик запросов, инвалидируемый при новом поиске, закрытии и смене команды/сервера.

7. **P2 — настройки интерфейса сохраняются, но не применяются.**
   `useSettingsStore` используется только в `SettingsModal`. Например, `sendOnEnter` не читается редактором,
   `notificationsEnabled` не участвует в отправке уведомлений. Подключить каждый параметр к месту использования
   и покрыть поведенческими тестами.

8. **P1 — интерактивный диалог вызывает отсутствующую команду.**
   `src/components/message/InteractiveDialogModal.tsx:70,122` вызывает `submit_dialog`;
   такой Rust-команды/регистрации в `src-tauri/src` нет. Реализовать IPC и проверить отправку/отмену диалога.

9. **P2 — неверное уменьшение счётчика непрочитанных веток.**
   `src/stores/threadsStore.ts:112`: чтение любой неизвестной ветки уменьшает глобальный счётчик,
   если он больше числа известных непрочитанных веток. Повторное чтение того же ID может обнулить чужие непрочитанные.
   `incrementThreadUnread` также увеличивает счётчик каждый раз для неизвестного ID. Нужен явный учёт ID,
   согласованный с частично загруженным списком; текущий WS-обработчик вызывает increment только для известных ему веток.

10. **P2 — лишние пересчёты длинной ленты.**
    `MessageList` подписан на общий `posts`, а `MessageItem` — на весь `users` и `userThreads`.
    Изменение чужого канала/пользователя запускает обработку текущей ленты. DOM растёт при догрузке истории без виртуализации.
    Это подтверждённые пути лишней работы, но степень влияния на FPS ещё не измерена.
    Сначала профиль на большой истории, затем узкие селекторы/виртуализация.

## Проверки и ограничения

- 93 frontend-теста прошли (10 файлов), включая 12 новых проверок истории, очереди участников, аватаров и lazy-loading.
- Четыре теста аватаров и тест Mermaid падают на исходных реализациях. Три теста истории падают при возврате
  ошибочного расчёта страницы и удалении проверок отмены во временной копии. После возврата исправлений проходят.
- `npm run build`: успешно, TypeScript и production bundle. Осталось существующее предупреждение об ineffective dynamic import `threadsStore`.
- `npm run lint -- --quiet`: без ошибок. Исходный полный lint имел 42 предупреждения; массовая правка стиля не выполнялась.
- `rustfmt --check --edition 2021 src-tauri/src/commands/messages.rs src-tauri/src/mattermost/client.rs`: успешно.
- Полный `cargo test`/сборка Tauri не завершены: `src-tauri/Cargo.lock` и часть `target` имеют флаг macOS `dataless`;
  чтение блокируется. Это существенное ограничение проверки Rust-изменений, rustfmt не заменяет компиляцию.
- По той же причине исходный `npm test` получал таймауты запуска воркеров. Стек зависшего TypeScript-процесса
  показал ожидание `read`, открытый файл — выгруженный `@types/react/jsx-runtime.d.ts`.
  Во временной копии `/private/tmp/mammoth-audit.7tJ5JO` с зависимостями из неизменённого lock-файла тесты занимают около 3 секунд.
  Пул Vitest и версии зависимостей проекта не менялись.
- Проверки frontend выполнены на копии актуального `src`, включая сохранённые изменения WebSocket пользователя.
  Нативный GUI, реальный сервер и сетевые сценарии не запускались; Tauri IPC в тестах замокирован.
